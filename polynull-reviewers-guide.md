# Reviewer's guide to PolyNull library models

First, read the tests. `JSpecifyLibraryModelsTests` has an unignored test for `Optional.orElseGet`. `JSpecifyLibraryModelsTests` also checks that the existing conditional-return model for `Optional.orElse` uses the fallback’s nullness. `PolyNullLibraryModelsTests` has tests for `Optional.orElseGet` and `Map.computeIfAbsent`. It also has tests based on custom library models for our own code. `PolyNullMethods` has the code, and the corresponding library models are in `TestLibraryModels`. `LibraryModelsHandlerTest` has tests for the new `PolyNullLocation` data structure and for detection of duplicate library models and models containing only top-level locations.

Then, read the new code for modeling PolyNull in library models. `LibraryModels` adds a new `polyNullLocations` method, based on the new `PolyNullLocation` data structure. Each modeled method must have at least one `@PolyNull` location with a non-empty type path; relationships involving only top-level nullness should use existing conditional-return or contract models. Note that we do not handle `Receiver` poly-null locations yet; those fail fast for now and will be handled in a follow up.

Various methods in `LibraryModelsHandler` have been updated. In `onOverrideMethodInvocationParametersNullability`, we treat argument positions that are `@PolyNull` at the top level as `@Nullable`; if that is incompatible with other `@PolyNull` positions at a call site, we’ll get an error in `GenericsChecks` when handling it.

We add built-in JDK library polynull models for `Optional.orElseGet` and `Map.computeIfAbsent`. `Optional.orElse` continues to use its existing conditional-return model.

The `CombinedLibraryModels` type is updated to include polynull models. It validates locations once per modeled method, rejects models with only top-level locations, and fails if polynull models for the same method come from multiple `LibraryModels` objects. It also facilitates polynull models taking priority over nullable and nonnull models at the same annotation location. (We need this to override `@Nullable` annotations with `@PolyNull` in the JSpecify JDK models.)

In `OptimizedLibraryModels` we add new logic so that a library model of `@Nullable` or `@NonNull` on an overriding method is ignored if an overridden method is `@PolyNull` in that location.  We don't really need this functionality yet for the JSpecify JDK, but it's consistent with the policy of `@PolyNull` models having priorities.

Before reading that reasoning, look at `NestedTypePathUpdater`, renamed from `AddAnnotationToNestedTypeVisitor`. It now supports replacing the type at a path, in addition to adding an annotation. We use replacement to build types for inference, and annotation updates to apply the inferred nullness afterward. There is some special handling for wildcards and captures to support both operations while preserving the existing wildcard-bound behavior.

Then, read the new `PolyNullInference` class. The key idea is to reuse our existing generic nullability constraint solver. For each invocation, `createContext` creates one synthetic type variable with a nullable upper bound, and builds a method-type overlay with that variable replacing every modeled `@PolyNull` location. All polynull locations for a call share this variable; different invocations get different variables.

With this overlay, ordinary subtype constraints express the polynull requirements. For example, a nullable argument at a top-level polynull parameter forces the variable to be nullable. Invariant positions like `List<@PolyNull Object>` can constrain it in both directions, so passing both `List<Object>` and `List<@Nullable Object>` at linked positions fails. A result target can also constrain the variable. Once inference succeeds, `applyToMethodType` writes the resolved `@Nullable` or `@NonNull` qualifier at every modeled location in the actual method type.

Most of the remaining changes are in `GenericsChecks`. Start with `generateConstraintsForCall`. For modeled calls, it registers the synthetic polynull variable and generates constraints against both the ordinary method type and the polynull overlay. Keeping the ordinary constraints means we still check and infer the method’s actual type variables. The additional overlay constraints link the modeled nullness positions. Both sets of constraints go through the same solver run.

The polynull contexts are threaded through constraint generation for nested calls, conditionals, and lambda return expressions. This lets the existing machinery for named functional-interface values, lambdas, and method references constrain the synthetic variable too. `InferenceSuccess` now records the resolved polynull nullness by invocation, alongside the ordinary type-variable solution. When caching inferred lambda and method-reference types, we use the overlay so those types reflect the polynull solution as well.

Next, look at `getInvokedMethodTypeAtCall` and `substituteTypeArgsInGenericMethodType`. We apply the resolved polynull annotations after substituting receiver and method type arguments and applying ordinary library models. For generic calls with inferred type arguments, we reuse the jointly inferred polynull result.

For non-generic calls and generic calls with explicit type arguments, `inferPolyNullnessSeparately` performs a separate solver run using the substituted method type. It reuses the same argument-constraint machinery. `addPolyNullResultConstraintsFromDirectAssignmentContext` also incorporates a directly enclosing assignment, variable initializer, return, or conditional-expression target. Successful results outside dataflow are cached separately, and the new cache is cleared in `clearCache`.

Inference failures involving the synthetic variable get a diagnostic about polymorphic nullness being constrained to both `@NonNull` and `@Nullable`, rather than exposing the synthetic variable name. The separate inference path also reports this diagnostic and uses the existing tracking to avoid duplicate reports.

Finally, look at how the inferred result reaches callers. `inferCallType` applies the resolved polynull annotation to generic call results, which also allows it to propagate through `var` locals. `getGenericReturnNullnessAtInvocation` now reads nullness from the resolved method type, and `NullAway.mayBeNullMethodCall` invokes it for polynull-modeled methods even when their declared return type is not a type variable. `getTypeNullnessForRead` also honors an explicit inferred `@NonNull` annotation before falling back to a capture’s nullable upper bound; otherwise, that fallback could discard the polynull result.
